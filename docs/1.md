理解修正如下：PostgreSQL 和 Redis 继续使用 Docker 中现有服务，但 API 不再构建或启动 Docker 容器，而是直接在本机用当前代码启动。

操作方案
1. 检查当前环境
确认当前 Git 工作区和最新提交状态。
确认 Docker 中 PostgreSQL、Redis 正常运行。
确认 Docker API 容器保持停止，不进行构建、重建或启动。
检查本机 8000 端口可用。
2. 准备本机连接 Docker 基础设施的环境变量
保留现有 .env 内容，不修改文件，只在当前启动命令中临时覆盖连接地址：

DATABASE_URL：沿用现有数据库名称、用户名和密码，只把 Docker 内部主机名替换为 127.0.0.1:5432。
REDIS_URL：沿用现有 Redis DB，只把 Docker 内部主机名替换为 127.0.0.1:6379。
JWT、Issuer、Audience、Redis Prefix 等其他配置继续使用现有 .env。
连接信息不会打印到终端，也不会生成新的环境文件。

3. 从本机更新 Docker PostgreSQL
在本机 PDM 环境中执行 Alembic 和 Seed，但目标是 Docker PostgreSQL：


pdm run alembic-current
pdm run migrate
pdm run seed
pdm run alembic-current

pdm run permission-sync --dry-run
pdm run permission-sync
pdm run permission-sync --check
预期结果：

数据库升级到 0002_user_management (head)。
已有用户数据保留。
管理员 Seed 幂等补齐全部用户管理权限。
不执行 downgrade、清库或删除 Volume。
不运行 Docker 一次性 API 容器。
之后会通过数据库查询确认：

Alembic revision 正确。
admin 角色存在。
Seed 管理员关联 admin 角色。
9 项细粒度用户管理权限及兼容的 user:write 均已存在。
4. 在本机启动 API
使用当前代码直接启动：


pdm run dev
实际执行时会在后台启动，并把日志放到临时目录，避免污染仓库；同时记录进程 PID，便于后续停止。

本机 API 地址：

http://127.0.0.1:8000
http://127.0.0.1:8000/docs
5. 启动后验证
依次验证：

GET http://127.0.0.1:8000/health 返回 200。
OpenAPI 中存在全部 /admin/users 路由。
使用本地 Seed 管理员登录。
调用 GET /admin/users，确认认证、权限、Docker PostgreSQL 和 Docker Redis 链路正常。
调用 logout 清理本次验证 Session。
检查本机 API 日志中没有数据库、Redis、迁移或 5xx 错误。
验证过程只读取用户列表，不创建、编辑、禁用或拉黑业务用户。

nginx 说明
当前 Docker nginx 的 upstream 是 Docker 网络中的 api:8000，不会自动代理到本机启动的 API。因此：

本次直接使用 http://127.0.0.1:8000 验证。
http://127.0.0.1:8080 可能因为 Docker API 容器停止而返回 502，这是预期现象。
本次不修改 nginx 配置，也不启动 Docker API。
失败处理
Alembic 或 Seed 失败：停止后续操作，不启动本机 API，不做数据库降级。
本机 API 启动失败：停止本机进程并查看临时日志，不修改 Docker PostgreSQL/Redis。
不执行 docker compose down、down -v、FLUSHDB 或任何数据删除操作。
最终目标是：Docker 只运行 PostgreSQL 和 Redis；数据库迁移与 Seed 由本机代码更新；最新用户模块 API 在本机 8000 端口运行。
