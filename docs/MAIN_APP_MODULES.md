# 主应用后台管理模块规划

## 问题

以下模块是否可以放在主应用中，还缺少哪些模块？

```text
面板（dashboard）
  注册用户、新增用户

用户管理（user）
  添加、编辑、删除、拉黑、恢复、权限编辑

子应用管理（app）
  添加、编辑、删除、禁用

权限管理（permission）
  新增、编辑、删除

角色管理（role）
  新增、编辑、删除、禁用

记录管理（log）
  登录、注册、报错
```

## 回答

可以。上述模块整体上都适合放在主应用，前提是主应用定位为**平台管理中心、统一身份与权限中心**，而不是业务数据管理中心。

## 一、适合放在主应用的模块

### 1. 面板 Dashboard

面板可以放在主应用，建议主要展示平台级数据：

- 用户总数、启用用户数、禁用用户数；
- 最近注册用户；
- 最近登录情况；
- 子应用数量及运行状态；
- 角色、权限数量；
- 最近安全事件；
- 最近管理员操作；
- 各子应用的访问量或错误数。

如果要展示订单、项目、库存等业务指标，建议由各个 `python-app` 提供统计 API，主应用只负责聚合展示，不直接查询业务数据库。

### 2. 用户管理 User

适合放在主应用，包括：

- 新增用户； ✅
- 编辑用户；✅
- 禁用、启用用户；✅
- 拉黑、恢复；✅
- 重置密码；✅
- 强制下线；✅
- 查看登录设备和登录记录；
- 分配角色；
- 分配组织或部门；
- 配置 MFA；
- 查看用户最近操作。

建议不要默认提供“直接修改用户权限”的操作，而是以**分配角色**为主：

```text
用户 -> 分配角色 -> 角色拥有权限
```

如果确实需要特殊授权，可以增加：

```text
用户 -> 单独授予或拒绝某些权限
```

个人权限覆盖会增加权限判断复杂度，建议作为后续功能。

“删除用户”最好采用软删除或归档，而不是直接物理删除，避免破坏历史日志和业务数据关联。

### 3. 子应用管理 App

适合放在主应用，包括：

- 新增子应用；✅
- 编辑子应用信息；✅
- 启用、禁用子应用；✅
- 配置应用名称、图标、访问地址、和服务账号；✅
- App Secret重新生成；✅
- 配置应用编码；
- 配置菜单或入口；
- 配置回调地址；
- 配置应用允许的权限范围；
- 配置服务调用权限；
- 查看应用访问状态；
- 生成或轮换应用凭证。

示例：

```text
应用名称：项目管理
应用编码：project
访问地址：https://project.example.com
状态：enabled
允许的权限范围：project:read project:write
```

如果子应用需要调用主应用或被主应用调用，还需要管理：

- App ID；
- App Secret；
- 服务账号；
- OAuth 回调地址；
- Token Scope；
- 密钥轮换和吊销。

`App Secret` 只应在创建时显示一次，不能在列表中明文展示。

### 4. 权限管理 Permission

适合放在主应用。

建议权限采用稳定的编码，例如：

```text
user:read
user:create
user:update
user:disable
role:read
role:update
app:manage
audit:read
```

权限至少包含：

```text
权限编码
权限名称
所属应用
资源
操作
状态
描述
```

推荐使用“资源:操作”的格式：

```text
order:read
order:create
order:update
order:delete
```

权限编码一旦被代码使用后，尽量不要修改，也不建议随意物理删除。可以改为禁用，或者标记为废弃。

### 5. 角色管理 Role

适合放在主应用，包括：

- 新增角色；✅
- 编辑角色；✅
- 删除或归档角色；✅
- 启用、禁用角色；✅
- 给角色分配权限；✅
- 给用户分配角色；✅
- 查看角色使用情况；
- 查看角色关联的用户和业务绑定；
- 查看角色变更记录。

角色建议分成两类：

```text
系统角色：平台预置，例如 super_admin、security_admin
自定义角色：管理员创建，例如 operator、auditor
```

系统角色不能随意删除，核心权限也不应允许普通管理员修改。

角色删除前，建议先检查：

```text
该角色是否被用户使用
该角色是否被业务数据引用
该角色是否被子应用使用
```

如果仍被使用，优先设置为 `disabled`，而不是物理删除。

### 6. 记录管理 Log

适合放在主应用，但最好不要把所有日志混在一起，建议改名并拆分为“审计与日志”。

#### 登录日志

记录：

- 登录成功；
- 登录失败；
- 登出；
- Token 刷新；
- 密码修改；
- 密码重置；
- MFA 验证；
- 登录 IP；
- User-Agent；
- 设备信息；
- 失败原因分类。

#### 操作审计日志

记录管理员对系统执行的操作：

```text
谁
在什么时间
从哪里
对什么对象
执行了什么操作
操作前是什么状态
操作后是什么状态
是否成功
请求追踪 ID
```

例如：

```text
管理员 user-001
禁用了角色 role-001
操作结果：成功
来源 IP：192.168.1.10
```

#### 安全事件

例如：

- 多次登录失败；
- 异常 IP；
- Token 吊销；
- 服务凭证轮换；
- 权限配置变化；
- 账号被锁定；
- 账号被解锁。

#### 系统运行日志

例如：

- Python 异常堆栈；
- Nginx 日志；
- Redis 错误；
- PostgreSQL 错误；
- 容器日志。

系统运行日志通常不建议长期全部存到主应用数据库。生产环境可以接入 ELK、Loki 或云日志平台，主应用主要提供关键审计日志和安全日志查询。

## 二、建议补充的核心模块

### 1. 组织与租户管理

如果未来存在多组织、多部门或多租户，建议增加：

```text
组织管理（organization / tenant）
```

包括：

- 新增、编辑、禁用组织；
- 部门管理；
- 用户所属组织和部门；
- 组织管理员；
- 组织级角色；
- 租户级数据隔离。

关系可以是：

```text
租户/组织
    -> 部门
    -> 用户
    -> 角色
    -> 子应用
```

如果当前是单企业私有化部署，也可以预留组织模型，第一版只创建一个默认组织。

### 2. 会话与登录安全管理

建议增加会话管理（session），包括：

- 当前在线会话；
- 登录设备；
- 登录 IP；
- 最后活跃时间；
- 强制下线；
- 全部下线；
- Token 吊销；
- Token 黑名单；
- 登录失败次数；
- 账号锁定；
- 登录策略。

这与 Access Token、Refresh Token 和 Redis 黑名单设计相对应。

### 3. 服务账号与 API 客户端管理

由于 `python-main` 和 `python-app` 之间会进行服务调用，建议增加：

```text
服务账号管理（service account）
API 客户端管理（API client）
```

典型调用场景：

```text
python-main -> python-app
定时任务 -> python-main
第三方系统 -> python-main
```

需要管理：

- 服务账号；
- App ID；
- App Secret；
- API Key；
- 允许访问的接口；
- Scope；
- 有效期；
- 吊销；
- 密钥轮换；
- 最近调用时间。

服务账号不是人类用户，不应与普通用户混淆。

### 4. 系统设置

建议增加系统设置（settings），可以包含：

- 系统名称和 Logo；
- 默认语言和时区；
- 登录页配置；
- 密码复杂度；
- Token 和 Session 有效期；
- 登录失败锁定策略；
- MFA 策略；
- 邮件 SMTP；
- 短信配置；
- 文件存储配置；
- CORS 配置；
- 安全策略；
- 日志保留时间。

涉及密钥和密码的设置必须加密保存，不能直接明文存储或写入日志。

### 5. 菜单与导航管理

如果子应用由主应用统一展示，可以增加菜单管理（menu），用于配置：

- 主应用菜单；
- 子应用入口；
- 菜单顺序；
- 菜单图标；
- 菜单访问地址；
- 菜单需要的权限；
- 菜单是否显示。

需要区分：

```text
权限：控制能不能访问
菜单：控制界面上是否显示
```

隐藏菜单不能代替后端鉴权，后端 API 仍然必须检查权限。

### 6. 通知与消息中心

可以增加通知管理（notification），例如：

- 系统通知；
- 账号被禁用通知；
- 密码即将过期；
- 安全告警；
- 角色变更通知；
- 子应用异常通知；
- 邮件或站内信。

第一版可以只做站内消息，后续再接邮件、短信或企业微信。

### 7. 回收站与归档管理

由于用户、角色和应用不建议随意物理删除，可以增加回收站或归档管理，支持：

- 查看已归档用户；
- 查看已禁用角色；
- 恢复对象；
- 永久删除；
- 查看删除人和删除时间。

对于角色尤其重要，因为业务应用可能保存了角色 ID 的逻辑引用。

### 8. 对外认证集成管理

如果系统需要接入企业已有身份系统，可以预留认证集成（integration），例如：

- LDAP；
- Active Directory；
- OAuth2；
- OIDC；
- SAML；
- 企业微信；
- 钉钉；
- 飞书。

私有化客户通常比较容易提出这类需求，可以放到后续版本。

### 9. 系统状态与运维管理

私有化部署通常还需要系统状态或运维管理，包括：

- 主应用状态；
- 子应用状态；
- Redis 状态；
- PostgreSQL 状态；
- 消息队列状态；
- 版本信息；
- 服务健康检查；
- 后台任务状态；
- 事件堆积情况；
- 失败任务重试；
- 数据备份状态。

第一版可以只做简单的健康检查页面，不一定需要实现完整监控平台。

## 三、推荐的主应用菜单结构

```text
面板
├── 平台概览
├── 安全概览
└── 服务状态

身份与组织
├── 用户管理
├── 组织管理
├── 部门管理
├── 会话管理
└── 登录安全

访问控制
├── 角色管理
├── 权限管理
└── 菜单管理

应用与集成
├── 子应用管理
├── 服务账号
├── API 客户端
└── 认证集成

系统管理
├── 系统设置
├── 通知管理
├── 回收站
└── 任务中心

审计与日志
├── 登录日志
├── 操作审计
├── 安全事件
└── 系统日志
```

## 四、不应该放在主应用的内容

主应用不应该直接管理业务应用内部的业务数据，例如：

```text
订单
项目
库存
合同
工单
业务审批
业务报表
业务角色规则
```

这些内容应由对应的 `python-app` 自己管理。

主应用可以提供：

- 用户身份；
- 角色；
- 权限；
- 子应用注册；
- 统一菜单；
- 访问控制；
- 审计；
- 平台级统计。

业务应用负责：

- 自己的数据库；
- 自己的业务接口；
- 自己的业务页面；
- 自己的业务规则；
- 对主应用角色 ID 的逻辑引用。

## 五、建议的开发优先级

### 第一阶段：基础平台

```text
Dashboard
用户管理
子应用管理
角色管理
权限管理
登录日志
操作审计
```

### 第二阶段：安全和组织

```text
组织/部门管理
会话管理
强制下线
密码策略
MFA
服务账号
API 客户端
```

### 第三阶段：平台化能力

```text
系统设置
菜单管理
通知中心
任务中心
回收站
服务状态
LDAP/OIDC/SAML 集成
```

## 结论

上述六个模块可以放在主应用，而且是主应用的核心模块。主应用建议定位为：

> **统一身份认证、权限控制、子应用管理和平台审计中心。**

最需要优先补充的是：

1. 组织与租户管理；
2. 会话与登录安全；
3. 服务账号与 API 客户端；
4. 系统设置；
5. 操作审计；
6. 菜单管理；
7. 服务状态与任务中心。

“记录管理”建议改名或拆分为“审计与日志”，重点保留管理员操作审计和安全事件，而不是把所有基础设施日志都保存到主应用数据库。
